# v0.9 Wan2.2 developer qualification notes

Status: experimental support scope accepted by the project owner; not a claim of
complete numerical qualification or an announcement that v0.9 has been released.

The owner accepts remaining Wan2.2 numerical/behavioral uncertainty when it is
clearly documented. Completing universal BF16 reference conformance is no longer
a prerequisite for delivering this explicitly limited feature. Existing numerical
tests, thresholds, failures and HOLD records remain unchanged. Acceptance of risk
is not a numerical test PASS.

## Supported evidence scope

Three representative Wan2.2-T2V-A14B videos were generated through the native
Product evaluation entry using the default Backend, native text conditioning,
declared execution/sampling programs, native decoding and media output. No Python
production inference or research numerical bridge was used by that entry.

Tested configuration: Linux, NVIDIA A800 80 GB, BF16, 832x480, 81 frames,
40-step declared UniPC schedule. A 30 GiB weight-cache budget reduced observed
whole-run GPU peaks to 44.80–44.81 GiB; generation took approximately 850–865 s.
The capped runs preserved the original three native output files exactly. The
owner judged the three native/official pairs similar in perceived quality and
prompt adherence. These are limited observations, not a general performance,
quality, memory-fit or deterministic cross-implementation guarantee.

The existing entry is documented in [Resource-bounded Product evaluation](../product/bounded-evaluation.md).
Its success state remains `EXECUTED_UNQUALIFIED`. Ordinary schema2 `run` is still
rejected by the current numerical admission guard. This document does not change
that guard or claim that the evaluation entry is already the ordinary run path.

## Known limitations

- Generic BF16 reference numerical qualification remains HOLD. Current production
  captures pass 110/110 local operator cases but 39/45 known FFN composition
  cases. A separate exposed full-FFN set passes 30/48. These are different suites,
  not video failure rates. Intermediate differences have not been shown to cause
  visible degradation in the three reviewed videos.
- Output differences, failures or memory exhaustion remain possible outside the
  tested prompts, shapes, lengths, device and environment. No incidence rate or
  guarantee for those configurations has been established.
- A separate shared F32 LayerNorm issue produces NaN on some fixed valid inputs.
  It is not proven to have affected the three BF16 videos and is not specific to
  Wan2.2. The isolated repair has not been adopted. This shared correctness issue
  remains disclosed independently; it must not be relabeled as a Wan2.2-only risk.
- A passing research route does not qualify another binary or production route.
  Versioned build, package and resource identities remain necessary.
- Full pretrained cross-model qualification is incomplete. Applicable legacy,
  synthetic graph, package and resource tests are evidence only for their stated
  scope; they do not prove all Wan2.1, LTX or Mochi workloads are unaffected.

## Delivery policy

Wan2.2 may be delivered with an explicit experimental support label and these
limitations. Its unresolved reference gate alone does not veto this limited
support scope. Do not relabel numerical HOLD as PASS, fit thresholds to failures,
or add model-specific Backend/CUDA/PrecisionPolicy behavior.

Changes to shared code must still preserve applicable existing-model regressions.
The owner accepted risk for Wan2.2; this is not permission to introduce regressions
in other models or weaken package identity, resource safety, finite/error checks,
or binding/program validation.

Moving experimental use to ordinary Product entry, if implemented, belongs to a
generic product qualification/admission policy with explicit support status.
It must not use `if model == Wan2.2`, change numerical dispatch, or implicitly
admit every schema2 package. No such implementation change is made here.

No new numerical candidates, commit, push or release are authorized by this
scope record. Release preparation may proceed around documented experimental
support; actual release readiness still requires an identified deliverable,
applicable compatibility checks and accurate user-facing entry documentation.
